How this works: a scheduled GitHub Actions workflow polls opensky-network.org/api/states/all for Berlin's bounding box every 5 minutes from GitHub's own runners (GitHub's practical floor for schedules — a 1-minute cron was tested and never actually fired), and commits the result to data/latest.json in this repo. This page just fetches that static file — on load, and every 60 seconds after — so there's no CORS problem and no server to run: the browser never talks to OpenSky directly. Between fetches, each marker keeps moving on its own, dead-reckoned from its last known fix using its reported heading and real speed (shown in the tag beside each plane), so motion is continuous even though the underlying data only updates every few minutes. The "on approach" / "climbing away" / "cruising" line in the narration and popups is a heuristic read of heading and altitude relative to Berlin's airport (BER) — not a real flight plan; OpenSky's free tier has no route data, and its historical-flights endpoint outright refuses anonymous requests. Operators are guessed from a small known- airline lookup table; an all-letters callsign with no flight number is flagged as a private aircraft's registration rather than "unidentified." If the data file is ever unreachable (or hasn't been generated yet), the dashboard falls back to a small set of animated stand-in flights, clearly marked DEMO DATA above, so the page never sits there broken.
